## Rebuild and check

After any source or README change, regenerate the description and build fresh
artifacts. Use a clean output directory; keep older validated artifacts separately.

```bash
python -m pip install build twine
python scripts/release/pypi_readme.py
python scripts/release/pypi_readme.py --check
python -m build --outdir dist/pypi-0.1.1
python -m twine check --strict \
  dist/pypi-0.1.1/mlx_one-0.1.1-py3-none-any.whl \
  dist/pypi-0.1.1/mlx_one-0.1.1.tar.gz
```

Rebuilding changes the artifact identities; repeat package/import checks and
regenerate hashes for the rebuilt files. The existing release workflow targets
the older restricted-alpha proof cohort; this local handoff does not claim it
has published the current 40-model cohort.

## Maintainer upload

For the prepared artifacts, verify their checksums and upload exactly these two
files using your PyPI account's existing authentication. Keep credentials out of
commands, source files and commits.

```bash
cd dist/pypi-0.1.1
shasum -a 256 -c SHA256SUMS
python -m twine upload --repository pypi \
  mlx_one-0.1.1-py3-none-any.whl \
  mlx_one-0.1.1.tar.gz
```

After the upload succeeds, verify the files and `pip install "mlx-one==0.1.1"`
from PyPI. Then update `publication_status`, `published` and
`published_install_version` in the release record. Update pending-publication
notices in the release notes, support status, getting-started guide and website
pages, then rebuild the documentation. The homepage release card reads the
release record; installation examples already use 0.1.1.
